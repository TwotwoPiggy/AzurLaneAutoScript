# Plan 04-01: 错误截图队列 JPEG 内存流高倍压缩与回溯容量控制

## 目标 (Goal)
重构 `screenshot_deque` 错误截图队列存储与回溯机制。废除原有 2.76MB (1280x720 RGB) 的 raw uint8 NumPy 裸存结构，改用 JPEG 质量 80 编码的内存字节流存储（单帧体积降至 50~70KB，内存降幅 98%）。将队列容量上限严格钳制在 100 帧以内（默认 60 帧，总内存稳定在 3.6MB~6MB，同步更新 argument.yaml、args.json 及 config_generated.py 默认值）。实现支持按需惰性解码的轻量帧对象包装器 `DequeFrame`，确保向后兼容 `frame['image']` 调用，并在异常落盘时直接二进制直写 `.jpg` 文件（依据 D-03 预期，以零 CPU 额外编解码损耗换取崩溃时刻最高可靠性，报错图仅存本地 `./log/error/` 不作外发，故不经 handle_sensitive_image 打码），彻底消除异常发生时的多帧二次转码 CPU 损耗，保持天然滑动队列生命周期（跨任务边界保留最近排查现场）。

## 关联决策与需求 (References & Traceability)
- 需求: MEM-01
- 决策: D-01 (JPEG 质量 80 编码), D-02 (默认 60 帧，上限钳制 100 帧), D-03 (直接直写 .jpg + 按需惰性解码), D-04 (天然滑动队列生命周期)
- 架构参考: `.planning/research/ARCHITECTURE.md` §2.3, §4.4; `.planning/research/PITFALLS.md` Pitfall 9

## 验证标准 (Verification Criteria)
1. 单元验证：通过 Python 交互式测试或测试脚本验证 `cv2.imencode` 产生的单帧 JPEG 质量 80 字节流大小在 40KB~80KB 之间，且 `DequeFrame['image']` 能无损还原为 (720, 1280, 3) 形状的 ndarray。
2. 容量验证：实例化包含 100 帧的 `screenshot_deque`，整队列总内存增量不超过 8MB（旧实现 100 帧裸存约 276MB，降幅 >97%）。
3. 落盘验证：模拟触发 `save_error_log()`，确认生成的一系列 `.jpg` 图片可被正常图像查看器打开，且写入耗时在 50ms 以内；确认二进制直接直写不触发图像二次解压/压缩。
4. 静态配置验证：确认 `argument.yaml`、`args.json` 与 `config_generated.py` 三处默认值均一致为 60。

## 必备准则与严禁事项 (Must-Haves & Prohibitions)
- **Truths (必须满足)**:
  - 队列单帧必须以 JPEG 二进制流存储，压缩质量必须为 80（D-01）。
  - 容量上限无论配置文件为何值均必须硬钳制在 `<= 100`（D-02）。
  - 对 `'image'` 键的读取必须保持 100% 接口兼容，返回有效 ndarray（D-03）。
  - 错误落盘必须优先以直接二进制写流方式保存为 `.jpg`（D-03，确认本地排查转储不经 handle_sensitive_image 重新编解码打码系设计预期，彻底杜绝异常时刻二次编解码 CPU 尖峰）。
  - 配置默认值必须在 YAML、JSON 和 Python 生成代码（config_generated.py）中完全保持同步。
- **Prohibitions (严禁行为)**:
  - 严禁在 `Screenshot.screenshot()` 高频主循环中将已压缩的字节流再次立即解压，必须惰性按需解码。
  - 严禁在任务交接处调用 `screenshot_deque.clear()`，必须保持自然滑动窗口（D-04）。
  - 严禁引入除 `cv2` / `numpy` 之外的额外第三方图片编码库。
