# Plan 04-02: Win32 物理工作集修剪工具封装与任务边界 GC 闭环

## 目标 (Goal)
构建跨平台的底层物理内存修剪与缓存回收屏障。创建 `module/base/memory_utils.py` 平台内存抽象工具库，封装 Win32 `EmptyWorkingSet`（优先通过 `GetCurrentProcess()` 支持工作子进程与 WebUI 主进程各自自管修剪，非 Windows 平滑降级）与 `get_process_rss()`、`trim_memory()` 接口。在 `module/base/resource.py` 的 `release_resources()` 中建立「模版/OCR 缓存注销 → `gc.collect()` 代际垃圾回收 → `empty_working_set()` 物理工作集归还」标准三部曲闭环。在 `alas.py` 的任务交接边界与调度长等待空闲阶段（`release_during_wait` / `wait_until`）触发修剪，有效缓解 15.8GB 虚拟内存环境下的换页颠簸与 OOM 风险。

## 关联决策与需求 (References & Traceability)
- 需求: MEM-02, MEM-03
- 决策: D-05 (触发时机：任务交接边界 + 调度器长等待空闲期), D-06 (三部曲标准闭环：缓存注销 -> gc.collect() -> EmptyWorkingSet()), D-07 (子进程 GetCurrentProcess 自管修剪与主进程看门狗自管修剪), D-08 (跨平台抽象适配库)

## 验证标准 (Verification Criteria)
1. 闭环验证：运行一段加载大量模版与 OCR 的脚本，随后调用 `release_resources()`，确认进程 RSS 显著降低，且 Python 堆中未被引用的垃圾对象被全代回收。
2. 边界验证：在 `alas.py` 调度循环中模拟任务完成与等待，确认内存修剪仅在任务切换点与等待阶段触发，核心战斗自律过程中零工作集修剪与 Stop-The-World 停顿。
3. 容错验证：在 Linux/容器环境中导入并调用 `memory_utils.py`，确认无 `AttributeError` 或 `OSError`，静默降级运行。

## 必备准则与严禁事项 (Must-Haves & Prohibitions)
- **Truths (必须满足)**:
  - 三部曲执行顺序必须严格保证为：模版与 OCR 缓存释放 -> `gc.collect()` -> `empty_working_set()`（D-06）。
  - 工作子进程与主进程各自必须使用 `GetCurrentProcess()` 自管修剪自身工作集，规避跨进程权限问题（D-07）。
  - 触发点必须严格限制在任务交接边界与调度器长等待空闲期（D-05）。
- **Prohibitions (严禁行为)**:
  - 严禁在高频截图轮询循环中触发 `gc.collect()` 或 `empty_working_set()`，防止引发 CPU 尖峰与 50ms 级别卡顿。
  - 严禁在非 Windows 平台上直接假设 `ctypes.windll` 存在，必须做好平台检查与异常捕获（D-08）。
