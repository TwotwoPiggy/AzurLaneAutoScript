# Plan 04-03: 多进程调度器子进程 RSS 巡检看门狗、主进程修剪与安全自愈

## 目标 (Goal)
构建多进程调度器子进程 RSS 巡检看门狗与安全自愈闭环。在 `alas.py` 中建立两阶段泄漏判定法（基线阈值 600MB，任务边界先深度修剪，若修剪后仍 >500MB 确认为底质泄漏）与 48 小时夜间（04:00~05:00）低峰期主动换茬机制；子进程仅在战役出击结算完毕、安全返回游戏主界面或进入任务调度队列待机点时执行毫秒级平滑热重启（保证 0 石油损耗与 0 扣分），并在退出前微小等待（`time.sleep(0.1)`）防止多进程日志队列截断。在 `module/webui/process_manager.py` 中持久化 `self.ev` 信号并实现单例幂等看门狗线程，精准区分「任务执行态」与「调度等待态」（180 秒僵死保底强杀仅在活跃任务期间生效，调度等待与维护期自动挂起杜绝误杀死循环），子进程退出后排空日志队列并自动响应 `Reason: Safe restart` 进行无缝热拉起；同时闭环 D-07 实现主进程自身低频工作集修剪（每 30 分钟），实现 7×24 小时无人值守高可靠运行。

## 关联决策与需求 (References & Traceability)

## 验证标准 (Verification Criteria)
1. 状态隔离验证：在 `alas.py` 处于 `wait_until` 长休眠（如等待 300 秒）或模拟维护期时，验证看门狗不会误判为僵死，子进程保持正常存活；而在任务执行过程中构造无日志挂起超过 180 秒时，看门狗准确在超时后执行强杀并拉起。
2. 队列防截断与自愈验证：测试子进程在任务边界触发 Safe restart，验证即使子进程立即退出，主进程通过 `time.sleep(0.1)` 与 `_drain_renderable_queue()` 机制仍能 100% 完整读取到退出原因，并在 1 秒内使用保存的 `self.ev` 完成热拉起。
3. 主进程工作集修剪验证：看门狗运行满 30 分钟或触发定时修剪时，验证主进程自身的 Working Set 显著下降（D-07 闭环）。
4. 线程生命周期验证：多次调用 `start()` 不会产生重复看门狗线程；调用 `stop()` 时看门狗线程与子进程同步干净退出。

## 必备准则与严禁事项 (Must-Haves & Prohibitions)
- **Truths (必须满足)**:
  - 180s 僵死超时判定必须严格仅在「任务执行态」生效，在 `wait_until` 及服务器维护等待期必须挂起（BLOCKER-1）。
  - 看门狗必须履行 D-07 职责，低频（每 30 分钟）对 WebUI 主进程自身执行工作集修剪（BLOCKER-2）。
  - 子进程退出前必须等待 0.1s 且主进程在退出时必须排空 IPC 日志队列，杜绝日志截断竞争（WARNING-1）。
  - `ProcessManager.start()` 必须保存 `ev` 到 `self.ev`，且看门狗线程必须幂等单例启动（WARNING-2）。
  - 必须采用两阶段泄漏判定：>600MB 先修剪，修剪后仍 >500MB 才标记重启（D-09）。
  - 重启时机必须严格限定在任务安全完成边界，保证 0 资源损耗与 0 扣分（D-10）。
  - 必须在连续运行 48 小时后选择夜间 04:00~05:00 这一安全空闲窗口执行主动换茬（D-12）。
- **Prohibitions (严禁行为)**:
  - 严禁在 `wait_until`、调度空闲或游戏维护期间对未输出日志的子进程进行 180s 超时强杀。
  - 严禁在战斗自律、结算界面或移动过程中触发自愈重启。
  - 严禁在主进程/WebUI 进程被手动调用 `stop()` 时看门狗误重启子进程。
  - 严禁重复拉起多个未受管的看门狗后台线程。
